# 国内快递对账Agent接入燕子调用体系方案 V1

> 编制：燕子 | 日期：2026-08-10 | 状态：待涛哥确认

---

## 一、调研结论速览

**【核心结论】** 当前扣子环境下，**Skill方式无法直接封装已有独立Agent**，但可以通过 **「Agent项目 + coze CLI调用」** 实现外层包装，让燕子能够程序化调用对账能力。

推荐方案：**方案B — 新建一个"快递对账调用层"Agent项目，通过coze-cli向其发送任务，由该Agent执行V1.0对账逻辑，结果通过文件 + 摘要返回。**

---

## 二、逐问答复

### 1. 当前环境能否使用Skill方式接入？

**不能直接用。**

Skill是「指令+代码」的能力包，运行在调用者的沙箱里。而国内快递对账Agent是一个**独立的Agent实体**，有自己的记忆、规则体系、对话上下文。Skill方式无法"包"住一个独立Agent。

但可以做一个**伪Skill**——把调用逻辑（通过coze-cli调对账Agent）封装进Skill，燕子skill_load后就能用。这本质上是给调用层包了层皮，不是真的把对账能力装进了Skill。

### 2. 能否使用Workflow作为统一入口？

**扣子支持workflow类型项目**（`coze code project create --type workflow`），但需要先把对账能力拆成可编排的节点。

问题在于：对账Agent的核心价值是它自己固化的V1.0生产规则和业务理解，这是一个LLM Agent能力，不是标准API节点。Workflow更适合串API和工具，不适合串一个完整Agent。

**不推荐作为主方案**，除非后续要把对账逻辑彻底API化。

### 3. 是否需要API？

**当前阶段不需要自建API。**

对账Agent本身没有对外API接口。如果走coze-cli调用Agent的方式，不需要额外建API。

未来如果要做更高程度的自动化（比如定时自动拉账单自动对账），可以考虑把对账核心逻辑做成独立服务再包API，但那是下一阶段的事。

### 4. 公司订单Excel如何传入？

两种路径：

- **路径A（推荐）**：燕子将文件存到工作目录 → 任务消息中带上文件绝对路径 → 对账Agent直接读取本地文件
- **路径B**：将文件上传到飞书/对象存储 → 传URL给对账Agent → 对账Agent下载后处理

**推荐路径A**，因为同在扣子云环境里，本地文件读取最快最稳，也不需要额外传文件权限。

### 5. 快递账单Excel如何传入？

同第4题，**本地文件路径传入**。

### 6. 生成的Excel如何返回？

对账Agent生成Excel → 保存到约定的输出目录 → 在回复中告诉燕子文件路径 → 燕子读取/转发。

这是最稳的方式。飞书消息里传大文件容易出问题，本地文件系统传递最可靠。

### 7. 如何保证调用的仍然是V1.0逻辑？

通过**三层锁定**：

1. **生产规则冻结**：对账Agent的ROLE/BUSINESS/SOP/CASES/TOOLS/MEMORY中明确标记"国内快递对账生产规则 V1.0"，禁止自行修改
2. **调用层只读**：燕子的调用层只传参数（月份/快递公司/文件路径），不传任何业务规则指令，不干预执行逻辑
3. **版本校验**：每次对账输出中附带"生产规则版本号"，燕子检查版本号是否为V1.0，不一致则升级涛哥

### 8. 是否需要新增权限？

**需要新增1项权限**：燕子侧通过coze-cli调用扣子Agent项目的权限。

具体来说：
- 已有：coze-cli已用涛哥PAT登录，有权限操作扣子空间内的项目
- 新增：无额外三方权限，不需要申请飞书/快递API等权限

**符合最小权限原则**——只开放"向对账Agent发消息 + 读取输出文件"的能力。

### 9. 需要新增哪些组件？

| 组件 | 用途 | 工作量 |
|------|------|--------|
| 「国内快递对账」Agent项目 | 在coze code中创建，承载V1.0对账逻辑 | 中（需迁移/重建） |
| 调用层脚本 | 燕子侧Python脚本，封装coze-cli调用逻辑，处理输入输出 | 小 |
| 约定目录结构 | 输入/输出文件的标准存放路径 | 极小 |
| Skill包装（可选） | 将调用脚本封装为Skill，方便燕子触发 | 小 |

### 10. 推荐最终方案是什么？

**【推荐方案：B — "调用层Agent + coze-cli"方案】**

架构图：
```
涛哥
 ↓
燕子（主Agent）
 ↓ 识别：CN｜国内物流｜快递对账
 ↓ 调用：快递对账调用层脚本
 ↓ （通过 coze code message send 向对账Agent发任务）
 ↓
「国内快递对账」Agent项目（coze code, agent类型）
 ↓ 执行V1.0生产规则
 ↓ 生成Excel到输出目录
 ↓ 返回对账摘要 + 异常摘要 + 文件路径
 ↓
燕子汇总
 ↓
涛哥
```

**为什么选这个方案：**

| 维度 | 评分 | 说明 |
|------|------|------|
| 最小改动 | ⭐⭐⭐⭐ | 不需要拆已有Agent，只需在coze code中建一个agent项目并把V1.0规则灌进去 |
| 稳定性 | ⭐⭐⭐⭐⭐ | 对账逻辑仍由专门的Agent执行，不混入燕子的上下文 |
| 可复用性 | ⭐⭐⭐⭐ | 调用层可以复用到其他专业Agent的接入 |
| 自动化程度 | ⭐⭐⭐⭐ | 燕子能全自动触发，不需要涛哥手动切换会话 |

**备选方案对比：**

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| A. Skill直接封装 | 最轻量 | Skill无法承载独立Agent的记忆和规则体系 | ❌ 不可行 |
| B. 调用层Agent + coze-cli | 不破坏生产规则、调用稳定、可复用 | 需要迁移对账Agent到coze code项目 | ✅ 推荐 |
| C. Workflow编排 | 可视化、高大上 | 不适合串完整Agent，需要拆成API节点 | ❌ 成本太高 |
| D. 文件中转+人工触发 | 完全不改动对账Agent | 无法自动触发，等于没接入 | ❌ 排除 |

### 11. 实施步骤是什么？

**阶段一：准备（1天）**
1. 在coze code中创建「国内快递对账」agent项目
2. 将国内快递对账生产规则V1.0完整注入该Agent（ROLE/BUSINESS/SOP/CASES/TOOLS/MEMORY）
3. 配置文件访问权限，确保能读写工作目录

**阶段二：联调测试（1-2天）**
4. 燕子侧编写调用层脚本，封装coze-cli调用
5. 使用2026年6月历史数据做全链路测试
   - 燕子触发 → 调用对账Agent → V1.0执行 → 返回Excel + 摘要 → 燕子汇报
6. 对比测试结果与原独立Agent运行结果，确保一致性

**阶段三：正式接入（0.5天）**
7. 验证通过后，更新登记册状态为"燕子可调用"
8. 更新燕子MEMORY中的调用路由规则

**阶段四：7月数据复测（0.5天）**
9. 用2026年7月数据再跑一次全链路，确认稳定

总计：约3-4天。关键路径是阶段二的联调和一致性验证。

### 12. 有什么风险？

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 对账Agent迁移到coze code项目后，V1.0规则有偏差 | 对账结果不一致 | 中 | 用6月、7月历史数据做一致性对比，偏差超过阈值则回退；逐步迁移逐项验证 |
| coze-cli调用不稳定（超时、网络问题） | 任务卡住或失败 | 低 | 调用层加超时控制和重试机制；失败时燕子手工兜底 |
| 文件路径约定混乱导致读错文件 | 对账数据错误 | 低 | 严格按"月份_快递公司"命名，调用前校验文件存在性和月份 |
| 对账Agent输出格式变动，燕子解析失败 | 无法汇总结果 | 低 | 定义标准输出JSON格式，对账Agent必须按格式返回；解析失败时升级涛哥 |
| 生产规则意外被修改 | 破坏V1.0基线 | 低 | 版本号校验机制 + 输出中附带版本号，燕子检查 |

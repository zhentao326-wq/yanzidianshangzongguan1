# 子Agent调度SOP V1

**版本：** V1.0
**生效日期：** 2026-08-18
**维护人：** 燕子（主Agent / AI调度中枢）
**审批人：** 涛哥（刘祯涛）
**适用范围：** 公司所有专业子Agent（在岗2个 + 规划中7个）

---

## 一、目的与适用范围

### 1.1 目的
规范公司所有专业子Agent的**派发、执行、验收、汇总**全流程，确保多Agent协作产出稳定、可靠、口径统一、可追溯，防止低质产出与信息失真。

### 1.2 适用范围
- **在岗子Agent（2个）：** TH利润核算、CN快递对账
- **规划中子Agent（7个）：** TH经营数据、TH商品、TH广告、内容创作、视觉、TH客服、TH风控
- 任何新上岗的子Agent，上岗即默认遵循本SOP

---

## 二、总体架构

**燕子现行调度模式 = Orchestrator-Worker + Supervisor 混合模式**（方向正确，无需推翻，按本SOP补强短板）。

| 角色 | 定位 | 职责 |
|------|------|------|
| 主Agent（燕子） | 统筹调度中枢（编排器 + 监督者） | 需求解析、任务拆解、派发台账、进度管控、结果校验、最终汇总 |
| 子Agent（Worker） | 垂直执行单元 | 按标准任务单执行，按标准回报格式回报，异常主动升级 |

**核心判断原则（先问"需不需要多Agent"）：**
> 多数任务不需要多Agent。单Agent + 好工具 + 紧凑prompt 在大量场景胜过 5-Agent 系统。
> 只有任务**真正跨专业可分离**时才值得引入子Agent——对应四步决策法第一步"能直接回答吗？能就自己答"。

---

## 三、子Agent调度六步闭环

### 3.1 需求解析
- 识别：核心目标、业务域（CN/TH/公共）、边界、交付要求、优先级
- 模糊需求先确认，形成**需求总纲**
- 输出：需求总纲（一段话：做什么、为什么做、给谁用、做到什么程度算完成）

### 3.2 任务拆解
- 按「领域边界清晰、任务无重叠、全覆盖需求目标」拆为独立子任务
- 每个子任务明确：目标 / 交付标准 / 时限
- 输出：任务清单

### 3.3 派发与台账
- 为每个子任务匹配对应子Agent
- 建立**任务台账**（见附录A），同步需求总纲与子任务要求
- 输出：标准任务单 + 台账记录

### 3.4 进度管控
- 跟踪执行状态，接收异常反馈
- 超时 / 不合格 → 修正指令、重跑或更换子Agent
- 关键节点（开始/卡住/需决策/完成）主动汇报

### 3.5 结果校验（Critic闭环）
- 对照验收清单（见第六章）逐一验收
- 不合格 → 打回重做并记录失败策略到黑名单；合格 → 归档
- 用 max_iterations 限制重试次数，防死循环

### 3.6 最终汇总
- 去重、逻辑串联、格式统一
- 按结果聚合三策略（见第七章）整合为可直接使用的最终成果
- 输出：管理层摘要 + 完整产物（存档）

## 四、标准任务单模板（主Agent→子Agent）

| 字段 | 说明 | 必填 |
|------|------|------|
| 任务ID | 如 T-20260818-001 | ✅ |
| 任务名称 | 清晰动作短语 | ✅ |
| 业务域 | CN国内 / TH泰国 / 公共 | ✅ |
| 派发时间 / 截止时间 | YYYY-MM-DD HH:MM | ✅ |
| 负责人 | 子Agent名称 | ✅ |
| 任务目标 | 一句话说明要达成的结果 | ✅ |
| 执行步骤 | 关键步骤与约束（不规定死，给方法与边界） | ⭕ |
| 输入文件/数据 | 数据源、文件路径、链接 | ⭕ |
| 交付标准 | 完成判定（数量/格式/口径） | ✅ |
| 优先级 | P0/P1/P2 | ✅ |
| 风险等级 | L1/L2/L3 | ✅ |

## 五、子Agent标准回报格式（子Agent→主Agent）

| 字段 | 说明 |
|------|------|
| 任务ID | 回填任务单ID |
| 执行状态 | 成功 / 部分完成 / 失败 / 需决策 |
| 完成内容 | 做了什么、做到哪一步 |
| 关键数据/口径 | 核心数字 + 采用口径（引用来源） |
| 异常与风险 | 发现的异常、风险、卡点 |
| 待确认事项 | 需要主Agent/涛哥拍板的问题 |
| 产出文件路径 | 产物存放位置 |

---

## 六、验收清单（Critic闭环）✅ 5项

1. **数据完整性**：所有要求字段都有，无空项、无"无数据"敷衍
2. **口径合规**：是否符合对应业务规则（如 TikTok利润核算规则V1.0冻结版、CN快递对账规则）
3. **来源可验证**：关键结论是否有官方/一手来源，禁止编造
4. **异常是否升级**：L2/L3风险是否按规定上报，是否带方案
5. **结果是否打回**：任一项不达标 → 打回重做，失败策略记入黑名单

---

## 七、结果聚合三策略

| 策略 | 适用场景 | 做法 |
|------|----------|------|
| 简单拼接 | 结果相互独立、无交叉 | 直接拼接，去重 |
| 结构化合并 | 结果可对比、需排序 | 统一schema/表格模板（如多店汇总统一表头） |
| 冲突解决 | 多源结果不一致 | 预设裁决规则：以冻结版业务规则为准，规则无覆盖则主Agent裁决 |

---

## 八、质量控制四件套

1. **防回声失真**：要求子Agent严格引用原始数据；汇总时回看原始输出而非中间转述版本
2. **Critic评审闭环**：Planner→Executor→Critic→Reporter，质量不达标打回重规划，失败策略记黑名单；max_iterations 限重试
3. **独立验证**：可信结论必须来源可验证（官方/一手源），反幻觉——只从已验证来源取数
4. **Token/成本预算**：并行子Agent默认 ≤3 个；每步输出做摘要压缩，只保留关键信息

---

## 九、异步长任务与人在回路

### 9.1 异步长任务
- 长任务（分钟~小时级）**异步执行**：先快速响应"已接单"
- 在 **开始 / 卡住 / 需决策 / 完成** 四个节点主动汇报，不让涛哥干等

### 9.2 状态持久化
- 任务状态、事件日志、产物、决策记录作为**可恢复对象持久化**，不依赖单一模型上下文窗口

### 9.3 人在回路（人工审批）
- L3级（资金/店铺/广告/商品/风控/人员重大决策）刻意插入人工审批关卡
- 属于**架构设计**而非自动化失败；先给方案再等涛哥拍板

---

## 十、风险三级分级

| 级别 | 定义 | 处理方式 |
|------|------|----------|
| L1 | 无需确认（翻译/文案/日报/内部任务） | 直接执行 |
| L2 | 有SOP且低风险 | 先判断再执行 |
| L3 | 资金/店铺/广告/商品/风控/人员重大决策 | 必须先经涛哥确认 |
